# Output Files

This document explains every file generated by the **Sub Domain Enumeration Tool for Linux**, its purpose, and how it can be used during reconnaissance, penetration testing, or bug bounty hunting.

---

# Output Directory Structure

After running the tool, an output directory similar to the following will be created.

```
recon_example/

├── passive_unique.txt
├── all_candidates_unique.txt
├── resolved_subdomains.txt
├── dns_records.txt
├── httpx.jsonl
├── live_urls.txt
├── live_with_status.txt
├── dns_alive_but_no_http.txt
├── vhost_candidates_ffuf.txt
└── raw/
```

The directory name depends on the target domain or the output directory specified by the user.

# passive_unique.txt

## Description

Contains every **unique passive subdomain** collected from:

- Subfinder
- Assetfinder
- Amass
- Findomain
- Sublist3r
- crt.sh

Duplicate entries are automatically removed.

## Example

```
api.example.com
mail.example.com
dev.example.com
vpn.example.com
```

## Typical Use

- Initial reconnaissance
- Asset inventory
- OSINT analysis

---

# all_candidates_unique.txt

## Description

Contains every candidate generated from:

- Passive Enumeration
- Gobuster
- AlterX
- Any additional discovery methods

Duplicates are removed.

This file usually contains the largest number of candidate subdomains.

## Example

```
api.example.com
dev-api.example.com
staging-api.example.com
admin.example.com
```

## Typical Use

Input for DNS validation.

---

# resolved_subdomains.txt

## Description

Contains only subdomains that successfully resolve via DNS.

Invalid entries are removed.

## Example

```
api.example.com
vpn.example.com
portal.example.com
```

## Typical Use

- HTTP probing
- Port scanning
- Vulnerability assessment

---

# dns_records.txt

## Description

Contains DNS information collected during validation.

Depending on configuration, records may include:

- A
- AAAA
- CNAME

## Example

```
api.example.com
A
104.21.xx.xx

cdn.example.com
CNAME
example.cloudflare.net
```

## Typical Use

- Infrastructure mapping
- CDN identification
- DNS analysis

---

# httpx.jsonl

## Description

Raw JSON output generated by ProjectDiscovery **httpx**.

This file contains detailed metadata for every responsive web service.

## Information Collected

- URL
- Status Code
- Content Length
- Response Time
- Page Title
- Technologies
- IP Address
- CNAME
- Redirect Location
- Web Server
- TLS Information (when available)

## Example

```json
{
  "url":"https://api.example.com",
  "status_code":200,
  "title":"API Portal",
  "tech":["nginx","PHP"]
}
```

## Typical Use

- Automation
- Scripting
- Importing into other tools
- Advanced filtering

---

# live_urls.txt

## Description

Contains only live web URLs.

## Example

```
https://api.example.com
https://portal.example.com
http://dev.example.com
```

## Typical Use

Perfect input for

- Nuclei
- Katana
- Hakrawler
- Crawlers
- Manual testing

---

# live_with_status.txt

## Description

Contains every live URL together with its HTTP status code.

## Example

```
200 https://portal.example.com

302 https://login.example.com

403 https://admin.example.com
```

## Typical Use

Quickly identify

- 200 OK
- Redirects
- Forbidden pages
- Interesting endpoints

---

# dns_alive_but_no_http.txt

## Description

Contains hosts that resolve successfully but do not expose HTTP or HTTPS services.

## Example

```
vpn.example.com

smtp.example.com

db.example.com
```

## Why It Matters

These systems may still expose services such as

- SSH
- FTP
- SMTP
- IMAP
- POP3
- VPN
- RDP
- Custom TCP services

## Recommended Next Step

Run

```bash
nmap -Pn -sV -iL dns_alive_but_no_http.txt
```

---

# vhost_candidates_ffuf.txt

## Description

Contains virtual hosts discovered using **ffuf**.

These hosts may not appear in normal DNS enumeration.

## Example

```
admin.example.com

internal.example.com

staging.example.com
```

## Typical Use

- Hidden applications
- Internal portals
- Development environments

---

# raw/

## Description

Stores intermediate files generated during execution.

Examples include

- Tool-specific outputs
- Temporary files
- Debug information
- API responses

These files are primarily intended for troubleshooting and advanced analysis.

# Suggested Workflow

After the tool completes:

## 1. Review Live Hosts

```
live_urls.txt
```

Run

```bash
cat live_urls.txt
```

---

## 2. Scan with Nuclei

```bash
nuclei -l live_urls.txt
```

---

## 3. Crawl Applications

```bash
katana -list live_urls.txt
```

or

```bash
hakrawler < live_urls.txt
```

---

## 4. Scan Non-Web Hosts

```bash
nmap -Pn -sV -iL dns_alive_but_no_http.txt
```

---

## 5. Review Rich Metadata

Inspect

```
httpx.jsonl
```

This file contains the most comprehensive information collected during HTTP probing.

---

# Notes

- Empty files are normal if no results are found for a particular stage.
- The number of discovered subdomains varies depending on the target.
- Results depend on the availability of passive data sources, DNS responses, and network connectivity.
- Larger targets typically produce more extensive output than smaller or newly registered domains.

---

# Best Practices

- Keep each scan in a separate output directory.
- Store results for future comparison.
- Compare outputs over time to identify newly exposed assets.
- Validate important findings manually before reporting them.
- Respect the scope and rules of any authorised engagement or bug bounty programme.

---

# Disclaimer

The generated output is intended for authorised security assessments, penetration testing, educational purposes, and bug bounty programmes where you have permission to test.

Always ensure that your activities comply with applicable laws and the target organisation's rules of engagement.
